# 基于 SSD 的过滤向量检索系统设计与性能分析

## 一、实验背景

大语言模型、检索增强生成和多模态检索通常将文本或图像表示为高维向量，同时使用类别、时间、权限或租户等结构化属性约束结果。过滤向量检索需要在满足属性条件的候选对象中寻找近邻。

当向量和图索引主体保存在 SSD 上时，过滤判断会改变图的可达性、节点扩展顺序和 SSD 访问行为。系统需要在 Recall、查询延迟、SSD I/O、DRAM 占用、索引大小和构建成本之间进行权衡。

本实验选取三类具有代表性的设计：

- PipeANN-Filter：通过推测式过滤及运行时策略选择降低属性访问和搜索开销；
- GateANN：通过 Pre-I/O Filtering 和 Graph Tunneling 避免不必要的 SSD 读取；
- Filtered-DiskANN：在构建阶段利用过滤标签组织 Filtered-Vamana 图，提高同标签节点的搜索可达性。

实验重点不是简单判断哪个系统更快，而是解释性能差异如何由系统机制及其资源代价产生。

## 二、学习目标

完成实验后，学生应能够：

1. 搭建并运行一个 SSD/on-disk 过滤向量检索系统；
2. 正确使用过滤 Ground Truth 计算 Recall@K；
3. 分析搜索预算和 Selectivity 对 Recall、延迟及 SSD I/O 的影响；
4. 将实验现象与图结构、过滤位置和数据访问机制联系起来；
5. 提出具有实验依据、能够验证且明确说明代价的优化方向。

## 三、统一数据集

课程使用 `YFCC Filtered Vector Search Course Dataset v1`。Base 保留原始 YFCC 多标签，每条课程查询从其原始标签中选择一个标签，统一谓词为：

```text
selected_label in point_labels
```

数据规模：

| Tier | Base 数量 | 维度与类型 | 用途 |
|---|---:|---|---|
| Debug | 100,000 | 192D uint8 | 环境、脚本和正确性调试 |
| Formal | 1,000,000 | 192D uint8 | 正式性能测试 |

过滤工作负载：

| Bucket | Formal 实际 Selectivity 范围 | 中位数 | 含义 |
|---|---:|---:|---|
| Low | 0.250%–0.851% | 0.545% | 强过滤 |
| Medium | 1.765%–4.995% | 2.958% | 中等过滤 |
| High | 7.074%–17.089% | 12.323% | 弱过滤 |

每档包含 5 个真实标签，每个标签 40 条查询，共 200 条。每条查询提供精确 L2 top-100 Ground Truth。

Debug 和 Formal 使用嵌套 Base 抽样以及同一组查询，但 Ground Truth 分别计算，禁止混用。真实标签的频率、语义、向量分布和 Selectivity 相互关联，因此实验结论应表述为真实工作负载分档比较，不能把所有性能差异单独归因于 Selectivity。

## 五、实验任务

### 任务一：系统复现与正确性验证

在 Debug 数据上完成环境配置、索引构建和过滤查询；随后在 Formal 数据上构建一次正式索引。

至少验证：

1. 查询数量与课程 workload 一致；
2. 每条查询返回 K 个结果；
3. 返回结果满足指定标签；
4. 距离度量与 Ground Truth 一致；
5. Recall@K 计算正确；
6. 查询实际使用 SSD/on-disk 路径，而非将完整索引预载入 DRAM。

记录正式索引的构建参数、构建时间、索引大小和峰值 DRAM；说明过滤信息是否参与索引构建，以及向量、邻接信息和过滤元数据如何组织。

仓库提供统一的适配器命令接口：

```bash
python3 adapters/<system>_adapter.py doctor ...
python3 adapters/<system>_adapter.py build ...
python3 adapters/<system>_adapter.py search ...
```

允许在不改变搜索语义的前提下扩展适配器。所有个人路径必须通过参数指定，禁止硬编码。

### 任务二：性能测试与系统分析

为控制工作量，正式实验只要求五个不同配置。

#### 实验 A：Recall–Latency

固定 `medium` workload，使用三档搜索预算：

```text
L = 20, 40, 80
```

如果所选系统不使用 L，应选择三个由低到高、作用等价的搜索预算，并说明参数含义。

每个配置至少统计：

- Recall@10；
- Mean Query Latency；
- QPS；
- 至少一项与核心设计相关的内部行为或资源指标。

绘制 Recall@10–Mean Latency 曲线，分析提高 Recall 所付出的搜索和 I/O 代价。

#### 实验 B：Selectivity–Performance

固定实验 A 的中等搜索预算，建议 `L=40`，分别测试：

```text
low / medium / high
```

其中 `medium, L=40` 已在实验 A 中完成，因此只需新增 low 和 high 两个配置。

至少报告实际 Selectivity、Recall@10、Mean Latency、QPS 和一项内部指标。固定搜索预算后，不同 Selectivity 的 Recall 可能不同；当 Recall 差异明显时，不得只根据延迟判断优劣。

#### 内部指标建议

- PipeANN-Filter：Pre/In/Post 路由比例、平均逻辑 I/O、false-positive exploration；
- GateANN：FilterSkips、平均 I/O、Tunnel 时间或 Process 时间；
- Filtered-DiskANN：平均 I/O、访问/扩展节点数、索引大小或构建开销。

SSD I/O 指标只统计 Query Phase，不包含数据转换、索引构建、索引加载、初始化和 Ground Truth 读取。优先使用系统内部逻辑 I/O；块设备物理 I/O Trace 属于扩展内容。

所有正式配置至少独立运行 3 次。必须采用相同的线程数、Top-K、查询集合、缓存协议和 I/O Backend，并报告中位数及波动范围。不同机器的绝对延迟不能直接用于系统优劣判断。

### 任务三：优化方向设计

根据系统机制和任务二的数据，按照以下结构提出一个优化方向，不要求实现：

```text
Observation
  -> Mechanism
  -> Bottleneck
  -> Optimization
  -> Expected Benefit
  -> Trade-off
  -> Validation Plan
```

- Observation：引用至少一项自己的实验结果；
- Mechanism：结合论文和源码解释现象；
- Bottleneck：区分实际测量和推断；
- Optimization：说明修改哪个阶段或数据结构；
- Expected Benefit：指出预期改善的指标；
- Trade-off：分析额外 CPU、DRAM、SSD 空间、构建时间或实现复杂度；
- Validation Plan：给出变量、对照组、指标和预期结果。

## 六、结果目录和统一字段

适配器将查询结果写入：

```text
course_runs/results/<system>/<tier>/<bucket>/<run-id>/
├── command.json
├── run.log
└── results.csv
```

`results.csv` 统一包含系统、数据规模、Selectivity 范围、L、K、线程、QPS、平均延迟、Recall 百分比、平均 I/O 及系统特有指标。某个系统没有直接输出的指标保持为空。

不得直接对多个标签的 QPS 做算术平均。整体 QPS 应按总查询数除以总执行时间计算。Recall 和延迟除整体统计外，建议报告逐标签分布。

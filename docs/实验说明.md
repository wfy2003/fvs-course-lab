# 基于 SSD 的过滤向量检索系统性能测试与设计比较

## 一、实验目标

过滤向量检索需要同时满足结构化过滤条件与向量近邻条件。当图索引主体位于 SSD 时，系统还需要权衡搜索可达性、过滤判断位置、SSD I/O、Recall、延迟和内存开销。

本实验比较两种具有不同设计思想的系统：

- **PipeANN-Filter**：在搜索过程中进行推测式过滤和动态路由选择；
- **GateANN**：通过 Pre-I/O Filtering 与 Graph Tunneling 避免无效 SSD 读取，并改善过滤后的图可达性。

完成实验后，应能够：

1. 运行 SSD/on-disk 过滤向量检索系统并正确读取 Recall@10；
2. 理解搜索预算对 Recall、查询延迟和 I/O 的影响；
3. 使用真实标签工作负载比较系统对过滤选择率变化的敏感性；
4. 根据测量结果解释两种系统机制及其资源代价；
5. 提出有证据、可验证且说明 Trade-off 的优化方向。

完成基础实验需要了解 PipeANN、PipeANN-Filter 和 GateANN 三篇论文的核心设计。无需掌握论文的全部细节，但应能够用相应机制解释实验结果。有余力的同学可以进一步了解 DiskANN 和 Filtered-DiskANN；这两篇论文不是基础实验的前置要求。论文、课程固定源码版本和建议阅读位置见 [参考文献与源码入口](参考资料.md)。

## 二、实验范围与工作量

- 完成方式：个人；
- 必做系统：PipeANN-Filter 和 GateANN；
- Debug 阶段：为两套系统各构建一次 10 万向量索引；
- Formal 阶段：使用课程提供的两套 100 万向量预构建索引，不要求重新构建；
- 每套系统每轮 5 个配置，两套系统共 10 行结果；
- 正式实验独立运行 3 轮；
- 优化部分只要求设计与验证计划，不要求实现。

Filtered-DiskANN 只作为自选扩展。完成扩展不会替代两套必做系统的实验。

## 三、统一数据集与查询语义

课程使用 `YFCC Filtered Vector Search Course Dataset v1`。Base 保留原始 YFCC 多标签，每条查询选择一个真实标签，过滤谓词统一为：

```text
selected_label in point_labels
```

| Tier | Base 数量 | 向量 | 用途 |
|---|---:|---|---|
| Debug | 100,000 | 192D uint8，L2 | 环境、构建和查询调试 |
| Formal | 1,000,000 | 192D uint8，L2 | 正式性能比较 |

Formal workload 分为三档：

| Bucket | 实际 Selectivity 范围 | 中位数 | 过滤强度 | 查询数 |
|---|---:|---:|---|---:|
| Low | 0.250%–0.851% | 0.545% | 强过滤 | 200 |
| Medium | 1.765%–4.995% | 2.958% | 中等过滤 | 200 |
| High | 7.074%–17.089% | 12.323% | 弱过滤 | 200 |

每档包含 5 个真实标签，每个标签 40 条查询；每条查询提供过滤后的精确 L2 top-100 Ground Truth。Debug 与 Formal 使用同一组查询，但分别计算 Ground Truth，禁止混用。

这些分桶同时包含标签频率、语义和向量分布差异。因此，实验可以比较真实过滤工作负载下的系统表现，但不能把桶间的全部差异严格归因于 Selectivity 单一变量。

## 四、固定环境与公平性规则

两套系统必须在同一台机器、同一 SSD 和相近系统状态下运行。正式测试统一使用：

| 参数 | 固定值 |
|---|---:|
| I/O Backend | Linux AIO |
| 查询线程 | 1 |
| Beam Width | 8 |
| Top-K | 10 |
| 内存图搜索预算 `mem_L` | 0 |
| 缓存预算 | 0 |
| GateANN FullAdj neighbors | 32 |
| 独立重复次数 | 3 |

正式参数由 `config/experiments.env` 和 `scripts/run_formal_experiments.sh` 统一设置。若因机器限制必须修改，应同时修改两套系统适用的公共参数，并在报告中说明原因。

系统内部 `L` 的含义相近，但数值尺度和 Recall 水平并不相同，因此不强求两套系统使用相同 L。课程固定参数是经过校准的三个从低到高的搜索预算：

| 系统 | High 上的三档 L | 代表性 L |
|---|---|---:|
| PipeANN-Filter | 20、40、80 | 40 |
| GateANN | 160、320、640 | 320 |

比较系统时必须同时观察 Recall 与延迟，不能把相同 L 当作公平性依据。

## 五、实验任务

### 任务一：复现与 Debug 验证

按照 [系统准备说明](系统准备.md) 获取课程固定提交并编译两套系统。课程统一使用 AIO；GateANN 准备脚本会应用一行编译兼容补丁，该补丁只修正 AIO control block 的数组访问，不改变算法与索引格式。

在 Debug 数据上完成：

1. 运行两套系统的 `doctor`，确认源码提交、数据和二进制；
2. 为每套系统构建一次 10 万向量索引；
3. 对 High workload 各执行一次过滤查询；
4. 检查查询进程正常结束、查询数为 200、返回 Recall@10 且结果文件非空；
5. 记录 Debug 索引构建是否成功及遇到的问题，不要求分析 Debug 性能。

统一适配器会把课程 Ground Truth 传给原系统查询程序，由原程序对全部返回结果计算 Recall@10。两套 Debug 索引构建完成后，执行：

```bash
bash scripts/run_debug_validation.sh
```

两套系统均输出 `DEBUG CORRECTNESS CHECK PASS` 才能进入正式实验。检查器会核对查询进程正常退出、查询数为 200、K/L/线程参数与课程设置一致，并要求 High workload 的 Recall@10 不低于 80%。无需自行实现 Ground Truth 或 Recall 工具。

### 任务二：正式性能测试

下载并校验两套 Formal 预构建索引后，执行：

```bash
bash scripts/run_formal_experiments.sh
```

脚本对每套系统完成以下 5 个唯一配置，并重复 3 轮：

| 实验目的 | Bucket | PipeANN L | GateANN L | 每轮新增行数 |
|---|---|---|---|---:|
| Recall–Latency | High | 20、40、80 | 160、320、640 | 3/系统 |
| Selectivity–Performance | Medium | 40 | 320 | 1/系统 |
| Selectivity–Performance | Low | 40 | 320 | 1/系统 |

High 的代表性配置已同时属于两组实验，因此不重复执行。每轮共 10 行，两套系统 3 轮共 30 行。

必须报告：

- Recall@10；
- Mean Query Latency 和 QPS；
- 平均逻辑 SSD I/O；
- PipeANN 的路由/过滤行为，或 GateANN 的 FilterSkips、Tunnel time、Process time；
- 查询进程峰值 RSS 与索引大小，作为资源背景；
- 3 轮结果的中位数和范围（或误差线）。

`elapsed_seconds` 是包含索引加载与初始化的进程总耗时，只作为诊断信息；性能图中的查询延迟应使用系统在 Query Phase 报告的 `mean_latency_us`。`mean_ios` 同样为系统内部 Query Phase 的逻辑 I/O，不等同于块设备物理 I/O。

需要完成两张核心图：

1. **Recall@10–Mean Latency 曲线**：High workload，分别连接每套系统的三档 L；
2. **Selectivity–Performance 图**：固定各系统代表性 L，横轴为 Low/Medium/High，至少展示 Recall、Mean Latency 和 Mean I/O。

分析时至少回答：

1. 增加搜索预算如何改变 Recall、延迟和 I/O？
2. 两套系统达到相近 Recall 时，性能和 I/O 是否仍有差异？
3. 过滤变强时，两套设计受到的影响有什么不同？
4. FilterSkips、Tunnel time 或 PipeANN 内部行为能否解释观察到的趋势？
5. 索引大小、内存占用与查询性能之间体现了什么 Trade-off？

### 任务三：优化方向设计

选择其中一套系统，根据任务二的数据提出一个优化方向，不要求实现。必须使用以下结构：

```text
Observation
  -> Mechanism
  -> Bottleneck
  -> Optimization
  -> Expected Benefit
  -> Trade-off
  -> Validation Plan
```

- **Observation**：引用至少一组自己的测量数据；
- **Mechanism**：结合论文或源码解释现象；
- **Bottleneck**：明确哪些是测量结论，哪些是推断；
- **Optimization**：说明修改的阶段、策略或数据结构；
- **Expected Benefit**：指出预期改善的指标和适用 workload；
- **Trade-off**：讨论 CPU、DRAM、SSD 空间、构建时间或复杂度；
- **Validation Plan**：给出对照组、自变量、控制变量、指标和可证伪的预期结果。

优化不以“想法数量”评分，重点是证据链是否完整、代价是否考虑充分、验证方法是否合理。

## 六、结果目录与字段

原始运行目录：

```text
course_runs/results/<system>/formal_1000000/<bucket>/<experiment-id>-rN/
├── command.json
├── run.log
├── results.csv
└── filter_config.json       # 仅 PipeANN
```

聚合文件：

```text
course_runs/experiments/<experiment-id>/
├── environment.txt
└── results.csv
```

统一结果包含系统、Bucket、实际 Selectivity 范围、L、K、线程数、QPS、平均延迟、Recall、平均 I/O、系统特有指标、源码 Commit、索引大小、进程总耗时和峰值 RSS。PipeANN 额外记录三种过滤路由的查询数及 false positives，GateANN 额外记录 FilterSkips 和时间分解；某系统不提供的字段保持为空。

绘图和统计应以 3 个重复的原始行计算。不要直接对多个标签或多轮 QPS 做算术累加；本课程适配器输出的 QPS 已由原系统基于整档 200 条查询统计。

报告结构可直接使用 [实验报告模板](实验报告模板.md)。评分关注：可复现性与正确性、数据呈现、机制解释、比较公平性，以及优化设计的证据链。

遇到错误时，先保留完整终端输出并运行对应适配器的 `doctor`。提问时请附系统名、源码 Commit、操作系统、`doctor` 输出、执行命令和完整错误日志。

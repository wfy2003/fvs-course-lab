# 结果分析指南

本文说明正式实验结束后如何读取、汇总和比较数据。这里规定数据处理方法和比较边界，但不预设哪套系统更优；系统机制、瓶颈和优化方向需要根据自己的结果判断。

## 一、确认实验完整完成

正式实验成功结束时，终端应出现：

```text
Collected and validated 30 rows: .../results.csv
Formal experiments complete: ...
```

若没有出现这两行，先排查失败的查询，不要分析不完整数据。默认实验生成：

```text
course_runs/experiments/<experiment-id>/
├── environment.txt
└── results.csv
```

- `results.csv`：两套系统、三档 Workload 和三轮重复的聚合数据，是统计与绘图的主要输入。
- `environment.txt`：CPU、内存、块设备、编译器、固定参数和源码版本，用于说明实验环境。

原始命令和日志位于：

```text
course_runs/results/<system>/formal_1000000/<bucket>/<experiment-id>-rN/
├── command.json
├── run.log
├── results.csv
└── filter_config.json       # 仅 PipeANN
```

聚合表出现异常值时，应回到对应的 `command.json` 和 `run.log` 核查，不要直接修改 CSV。

## 二、理解 30 行结果的组成

正式脚本每轮为每套系统运行 5 个唯一配置：

| 目的 | Bucket | PipeANN L | GateANN L | 每轮行数 |
| --- | --- | --- | --- | ---: |
| Recall–Latency | High | 20、40、80 | 160、320、640 | 3/系统 |
| Selectivity–Performance | Medium | 40 | 320 | 1/系统 |
| Selectivity–Performance | Low | 40 | 320 | 1/系统 |

每轮 10 行，默认重复 3 轮，共 30 行。High 中的代表性参数 `PipeANN L=40` 和 `GateANN L=320` 同时属于两组实验，因此不会重复执行。

## 三、核心字段

### 1. 实验身份与控制变量

| 字段 | 含义 |
| --- | --- |
| `repeat` | 重复轮次，默认取值为 1、2、3 |
| `run_id` | 单轮运行标识，用于定位原始目录 |
| `system` | `pipeann` 或 `gateann` |
| `tier` | 正式实验应为 `formal_1000000` |
| `bucket` | `low`、`medium` 或 `high` |
| `queries` | 该档查询数量，课程 Workload 为 200 |
| `L` | 系统的搜索预算；数值越大通常搜索越充分、开销也越大 |
| `k` | 返回近邻数，课程实验固定为 10 |
| `threads` | 查询线程数，课程实验固定为 1 |
| `beamwidth` | SSD 查询 beam width，课程实验固定为 8 |
| `system_commit` | 产生结果的第三方系统源码 Commit，应与课程固定版本一致 |
| `raw_log` | 该行数据对应的原始运行日志路径 |

PipeANN 和 GateANN 的 `L` 含义相近，但内部搜索行为不同，不能要求两套系统使用相同数值。比较时应寻找 Recall 相近的运行点。

### 2. Selectivity

| 字段 | 含义 |
| --- | --- |
| `selectivity_min` | 该 Bucket 中标签选择率的最小值 |
| `selectivity_median` | 该 Bucket 的代表性标签选择率 |
| `selectivity_max` | 该 Bucket 中标签选择率的最大值 |

Selectivity 表示满足过滤条件的 Base 向量比例：

```text
Selectivity 越低 → 满足条件的向量越少 → 过滤越强
Selectivity 越高 → 满足条件的向量越多 → 过滤越弱
```

绘图时优先使用 `selectivity_median` 作为横轴，并用 min/max 说明每档覆盖范围。Low、Medium、High 使用不同真实标签，因此不是严格的单变量实验。

### 3. 性能与正确性

| 字段 | 单位 | 含义与用法 |
| --- | --- | --- |
| `recall_percent` | % | Recall@10，已经是百分数，不要再次乘 100 |
| `mean_latency_us` | 微秒 | Query Phase 的平均查询延迟，性能图使用该字段 |
| `qps` | query/s | Query Phase 每秒查询数 |
| `mean_ios` | 次/查询 | 系统报告的平均逻辑 I/O，只用于解释内部行为 |
| `p999_latency_us` | 微秒 | 仅在原系统提供时有值；空白不代表 0 |
| `elapsed_seconds` | 秒 | 包含索引加载和初始化的子进程总时间，只用于诊断 |
| `peak_rss_kb` | KiB | 查询子进程峰值 RSS，用于资源背景 |
| `index_bytes` | byte | 对应索引文件总大小 |

不要用 `elapsed_seconds / queries` 代替查询延迟。当前固定为单线程，因此 `1,000,000 / qps` 通常接近 `mean_latency_us`，但报告应直接使用系统输出的延迟字段。

`mean_ios` 是逻辑 I/O，不等同于块设备统计的物理 I/O。当前版本中 PipeANN 与 GateANN 的 I/O 页面大小也不同，因此不能脱离 Recall、延迟和系统机制，仅根据 I/O 次数判定优劣。

### 4. PipeANN 专有字段

| 字段 | 含义 |
| --- | --- |
| `pre_filter_queries` | 路由到 Pre-filter 阶段的查询数 |
| `in_filter_queries` | 路由到 In-filter 阶段的查询数 |
| `post_filter_queries` | 路由到 Post-filter 阶段的查询数 |
| `filter_false_positives` | 系统报告并由适配器汇总的过滤假阳性指标 |

把三种路由查询数与 Selectivity、Recall、延迟、比较量和 I/O 联系起来，用于判断执行路径切换是否解释了性能变化。

### 5. GateANN 专有字段

| 字段 | 单位 | 含义 |
| --- | --- | --- |
| `filter_skips` | 次/查询 | 在发起 SSD I/O 前因过滤而跳过的候选 |
| `io_time_us` | 微秒/查询 | 系统报告的 I/O 时间 |
| `tunnel_time_us` | 微秒/查询 | Graph Tunneling 相关时间 |
| `process_time_us` | 微秒/查询 | 其他候选处理时间 |

分析时检查 FilterSkips 增加是否伴随 I/O、延迟或 Recall 变化，再结合 GateANN 的过滤前置和 Graph Tunneling 机制解释。不能仅凭一个时间字段就断言它是瓶颈。

某系统不提供的专有字段会保持空白。空白表示“不适用或未提供”，不是数值 0。

## 四、三轮结果如何汇总

按以下键进行分组：

```text
system + bucket + L
```

每组应包含 3 行。对 Recall、Mean Latency、QPS、Mean I/O 和所选内部指标分别计算：

- 中位数：作为表格和曲线的中心值；
- 最小值与最大值：作为范围，或绘制误差线；
- 必要时计算相对波动，但不要删除不利数据。

不要执行以下操作：

- 不要把三轮 QPS、I/O 或查询数相加后作为性能结果；
- 不要只选择最快的一轮；
- 不要把 High 的三档 L 合并为一个平均值；
- 不要把不同系统、Bucket 或 L 的行放进同一统计组。

建议先制作一张汇总表，至少包含：

```text
system, bucket, L,
selectivity_median,
recall_median, recall_min, recall_max,
latency_median, latency_min, latency_max,
qps_median,
mean_ios_median
```

## 五、两组必做图

### 1. Recall@10–Mean Latency

只选择 `bucket=high`：

- 横轴：三轮 `mean_latency_us` 的中位数，可换算为 ms；
- 纵轴：三轮 `recall_percent` 的中位数；
- 每套系统分别连接自己的 3 个 L；
- 用误差线或表格报告三轮范围；
- 在图例或点标记中注明 L。

比较两套系统时选择 Recall 相近的点。若 Recall 不同，应写成“在该测得运行点上”，不要把延迟差异直接解释成同等质量下的加速比。

### 2. Selectivity–Performance

固定：

```text
PipeANN L=40
GateANN L=320
```

对 Low、Medium、High 分别绘制或列表比较：

- Recall@10；
- Mean Latency；
- Mean I/O；
- 至少一项系统专有内部指标。

横轴可以使用 `selectivity_median`，也可以按 Low → Medium → High 排列，但必须标出实际 Selectivity。固定 L 实验用于观察工作负载敏感性，不是固定 Recall 质量下的性能排名；延迟降低但 Recall 同时下降时，不能只报告“系统变快”。

## 六、资源 Trade-off

将单位统一后再比较：

```text
index_size_GiB = index_bytes / 1024^3
peak_rss_MiB   = peak_rss_kb / 1024
```

`index_bytes` 在同一系统的多行中会重复，先确认其保持一致，再报告一个值。`peak_rss_kb` 可报告三轮中位数和范围。

资源分析至少回答：额外 SSD 空间或 DRAM 结构换来了什么 Recall、I/O 或延迟收益，又在哪类 Selectivity 下可能不值得。

## 七、从数据到机制解释

每个关键结论建议按以下顺序写：

```text
Observation（测量事实）
  → Internal Evidence（内部指标）
  → Mechanism（论文或源码机制）
  → Bottleneck/Hypothesis（瓶颈或待验证推断）
```

示例写法应引用自己的数据，但不要只写“曲线上升/下降”：

```text
当条件 A 变为 B 时，指标 X 从测量值 x 变化到 y；
同时内部指标 Z 发生……变化。
结合系统的……机制，这表明……；
但是否由……直接造成仍需通过……对照实验验证。
```

推荐检查的关系包括：

- L 增加时 Recall、Latency 和 Mean I/O 是否同步变化；
- PipeANN 的执行路径是否随 Selectivity 改变；
- GateANN 的 FilterSkips 与 Mean I/O、Tunnel time 是否相关；
- 达到相近 Recall 时，两系统的延迟和资源开销是否不同；
- 某个优化是否只是把开销从 SSD I/O 转移到了 CPU、DRAM 或索引空间。

## 八、公平性与结果边界

- 两套系统必须使用同一机器、数据集、Workload、线程数、K 和 I/O backend。
- 虚拟机结果可用于同一环境内的相对趋势分析，不应用来代表原生 SSD 的绝对性能。
- 不要跨同学、跨 PC 直接比较绝对 QPS；硬件和虚拟磁盘会显著影响数值。
- 200 条查询的运行时间可能较短，应报告三轮范围，并说明宿主机后台负载。
- 当前查询路径使用系统内部逻辑 I/O 统计，不要把它表述为操作系统实际完成的物理 I/O。
- 真实标签提高了场景真实性，但标签频率、候选分布和查询难度可能同时变化，因此 Selectivity 不是唯一变量。
- Formal 中某档 Recall 较低本身不代表程序失败；应结合参数和内部指标判断它是否反映系统敏感性。

## 九、提交前检查

- 聚合结果恰好包含默认的 30 行；
- 每个 `system + bucket + L` 组合都有 3 个重复；
- 图中使用 Query Phase 的 `mean_latency_us`，而不是 `elapsed_seconds`；
- Recall 保持百分数单位；
- 报告中给出中位数和范围或误差线；
- Selectivity 图标出了实际选择率；
- 比较延迟时同时说明 Recall；
- 空字段没有被错误填写为 0；
- 至少用一项系统专有指标解释机制；
- 优化方向包含收益、代价和可证伪的验证计划。
